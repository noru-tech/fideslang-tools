# W005: unknown field

**Severity:** warning, only with `--strict` · **Checked by:** [`src/validate/rules/schema.rs`](../../src/validate/rules/schema.rs)

**Rule:** with `--strict`, a resource should have only the top-level fields that the upstream
Fideslang models define for its type.

## What it checks

With `--strict`, `fl` compares each resource's top-level field names with the fields the upstream
models define for `organization`, `data_category`, `data_use`, `data_subject`, `dataset`, `system`
and `policy` (the IAB Tech Lab models and the fields Fides adds). Nested fields, such as those inside
collections or privacy declarations, are not checked. Without `--strict` the rule does not run.

## Why it matters

An unknown field is usually a typo (`privacy_declaration` for `privacy_declarations`,
`dataset_reference` for `dataset_references`). The intended field is then missing, and the other rules
say nothing because they never see it. Upstream tools may ignore or reject unknown fields. `fl`
itself keeps unknown fields through `cat`, `convert`, `merge` and `split`, which is why this check is
opt-in.

## Controls

None. This is a manifest hygiene check.

## Failing example

[`tests/fixtures/invalid/w005_unknown_field.yml`](../../tests/fixtures/invalid/w005_unknown_field.yml):

```yaml
system:
  - fides_key: extra_fields
    system_type: Service
    made_up_field: true
    privacy_declarations: []
```

```console
$ fl validate --strict tests/fixtures/invalid/w005_unknown_field.yml
tests/fixtures/invalid/w005_unknown_field.yml  system[extra_fields].made_up_field
  W005 unknown field `made_up_field` on system
see https://github.com/noru-tech/fideslang-tools/blob/main/docs/rules/W005.md
1 files, 1 resources checked against iab 3.0.0: 0 errors, 1 warning
```

Without `--strict` the same file passes:

```console
$ fl validate tests/fixtures/invalid/w005_unknown_field.yml
OK 1 files, 1 resources checked against iab 3.0.0: 0 errors, 0 warnings
```

## Passing example

[`tests/fixtures/valid/w005_known_fields.yml`](../../tests/fixtures/valid/w005_known_fields.yml):
the custom value lives under `meta`, the free-form mapping the models provide for it.

```yaml
system:
  - fides_key: meta_fields
    system_type: Service
    meta:
      made_up_field: true
    privacy_declarations: []
```

```console
$ fl validate --strict tests/fixtures/valid/w005_known_fields.yml
OK 1 files, 1 resources checked against iab 3.0.0: 0 errors, 0 warnings
```

## How to fix

- If the field is a typo, rename it to the intended field.
- If it is your own metadata on a dataset or system, move it under `meta`.
- If it is a field a newer Fides release added and `fl` does not know yet, please
  [open an issue](https://github.com/noru-tech/fideslang-tools/issues) so it can be added, and
  `--allow W005` in the meantime.

## Suppress or promote

W005 only runs with `--strict`. `--strict --deny W005` (or `--strict -W`) makes it fail the run, which
suits CI for hand-written manifests. `--allow W005` drops it.
