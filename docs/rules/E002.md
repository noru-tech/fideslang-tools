# E002: duplicate `fides_key`

**Severity:** error · **Checked by:** [`src/validate/rules/duplicates.rs`](../../src/validate/rules/duplicates.rs)

**Rule:** within one resource type, every `fides_key` must be unique across all the files loaded in
one run.

## What it checks

`fl` loads every file you name (directories recursively, in sorted path order), unions the resources
by type the way upstream's `ingest_manifests` does, and reports every resource whose `fides_key` was
already used by an earlier resource of the same type. The message names the file of the first
definition. The same key on two different types (a `system` and a `dataset` both called `billing`) is
allowed.

## Why it matters

Fides identifies a resource by its type and `fides_key`. Two definitions with the same key cannot
both exist once the manifests are pushed or merged: one is lost or replaces the other, and references
to the key become ambiguous. Duplicates usually come from a copied file or from two teams describing
the same system.

## Controls

None directly. This is a data map integrity check: it keeps one resource per key, so whatever you
derive from the data map describes each system or dataset once.

## Failing example

[`tests/fixtures/invalid/e002_duplicate_key.yml`](../../tests/fixtures/invalid/e002_duplicate_key.yml):

dataset:
  - fides_key: twice
    collections: []
  - fides_key: twice
    collections: []

## How to fix

- If both entries describe the same thing, keep one. `fl merge --dedupe PATH… -o merged.yml` keeps
  only the last definition of each duplicated key (later files win), so check that it is the one
  you want.
- If they are different things, give one of them a new key and update the references to it.
- To find every duplicate before merging, `fl merge --fail-on-duplicate PATH…` lists them and exits
  with `2`.

## Suppress or promote

E002 is already an error. `--allow E002` drops it from the report. Narrowing the run with `--type` or
`--key` also skips duplicates outside the selection.
