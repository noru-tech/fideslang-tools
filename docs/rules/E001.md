# E001: unknown taxonomy key

**Severity:** error · **Checked by:** [`src/validate/rules/keys.rs`](../../src/validate/rules/keys.rs)

**Rule:** every data category, data use and data subject key in a manifest must exist in the bundled
taxonomy or in a custom taxonomy resource loaded with it.

## What it checks

`fl` collects every value under `data_categories`, `shared_categories`, `data_use`, `data_uses`,
`data_purposes` and `data_subjects`, at any depth (privacy declarations, dataset collections and
fields, policy rules' `values`), plus the `parent_key` and `replaced_by` of custom
`data_category` / `data_use` / `data_subject` resources. Each key is looked up in the IAB Tech Lab
fideslang 3.0.0 taxonomy, extended with the custom taxonomy resources in the same manifest set.
When the key is unknown, `fl` suggests up to three similar keys.

## Why it matters

Fideslang labels only mean something if every tool reads them the same way. A key that is not in the
taxonomy (a typo, a key renamed in Fideslang 3.0, or a key from a downstream fork) cannot be resolved
by Fides, by policy evaluation or by anyone reading the data map, so the field, declaration or rule
that carries it is effectively unlabelled.

## Controls

If you derive a record of processing activities from your manifests, data uses are the purposes and
data categories and subjects are the categories of personal data and data subjects that GDPR
Art. 30(1)(b) and (c) ask for. An unknown key leaves a gap in that record. `fl` checks the label, not
whether the processing is lawful.

```yaml
system:
  - fides_key: bad_keys_system
    system_type: Service
    privacy_declarations:
      - name: uses keys that do not exist
        data_use: marketing.advertisin
        data_categories: [user.contact.emial]
        data_subjects: [custommer]
```

## How to fix

- Take the suggestion if it is the key you meant. Look a key up with `fl taxonomy show KEY`, or search
  with `fl taxonomy search WORD`.
- Manifests written before Fideslang 3.0 often use keys that were renamed (`user.cookie_id` is now
  `user.device.cookie_id`, `advertising` is now `marketing.advertising`). The suggestions usually
  find the new key.
- If the key is a deliberate extension, declare it as a custom `data_category`, `data_use` or
  `data_subject` resource in the manifest set, with a `parent_key` that is its dotted prefix (see
  [E004](E004.md)). `fl taxonomy diff PATH` shows what your custom resources add.

## Suppress or promote

E001 is already an error. `--allow E001` drops it from the report, which hides labels nobody can
interpret; prefer fixing the key. `--no-custom-taxonomy` turns custom taxonomy resources off, so keys
that only they define are reported as E001, which is how you check a manifest against the plain IAB
taxonomy.
